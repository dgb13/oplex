## Contexto

Hoy `User.tenantId` es 1:1 estricto (sin tabla de membresía) y el único
mecanismo cross-tenant que existe es la impersonación de `/admin`
(`AuthService.impersonate()`), atada al allowlist de email de
`PlatformAdminGuard` y con un problema de auditoría real: el JWT resultante
tiene `sub` = el usuario **destino**, así que toda acción queda indistinguible
de una acción genuina de ese usuario — no sirve como base para que un contador
externo actúe con su propia identidad en varios tenants.

Este plan diseña cómo una cuenta de contador accede a N tenants clientes,
entra a operar en cualquiera con alcance acotado, queda auditado como sí
mismo (no como un usuario prestado), y tiene una cartera consolidada con
vencimientos — reusando al máximo los mecanismos ya probados (RLS,
`withTenantContext`, `UserModuleAccess`, el patrón `list_tenant_ids()` +
loop de `AdminTenantsService`/`AdminAuditService`) en vez de inventar
paralelos nuevos.

**Verificado contra el código real** (no asumido): `buildAccessToken`/
`AuthService.login`/`impersonate()` completos, `JwtAuthGuard` (puramente
criptográfico, no re-consulta la DB por request), `/auth/me` (confía 100%
en RLS via `getTenantDb().user.findUnique({where:{id}})`, sin chequeo manual
de tenant), el flujo de `TeamInvitation` (single-tenant por construcción,
no reusable tal cual), `UserModuleAccess` (**sin ningún endpoint de
gestión hoy** — solo se lee en 4 lugares al emitir el JWT, nunca se
crea/actualiza vía API), las dos únicas policies RLS no-estándar del repo
(`tenants`/`audit_log`), el mecanismo exacto de `list_tenant_ids()`
(`SECURITY DEFINER`, `GRANT EXECUTE` acotado, llamado con el cliente Prisma
crudo antes de abrir `withTenantContext`), y el trigger de `AuditLog`
(`changedBy` sale de `current_setting('app.user_id', true)`, que
`TenantContextInterceptor` ya setea en cada request autenticado).

## 1. Modelo de membresía múltiple

**Actualizado tras confirmar con el usuario: el estudio contable es una
entidad compartida, no una cuenta individual.** Varios contadores de un
mismo estudio tienen que heredar la misma cartera de clientes. Esto cambia
el diseño de fondo respecto a la primera versión de este plan (que colgaba
la membresía de un `User` individual) — ahora cuelga de un **Tenant**.

**Decisión: el estudio contable ES un `Tenant` más de este sistema** (no un
concepto paralelo nuevo tipo "equipo"/"organización"). Reusa el 100% de lo
que ya existe: signup propio, `User`s propios (OWNER/ADMIN/staff) con login
real, roles ya definidos. Un estudio incluso podría llegar a usar Oplex para
su propio negocio (facturar honorarios) si quisiera, aunque eso no es
requisito. La alternativa (inventar una entidad "Firma"/"Equipo" separada de
`Tenant`) hubiera duplicado exactamente lo que `Tenant`+`User`+roles ya
resuelven — no se justifica.

**Decisión: nueva tabla `TenantMembership`, NO se toca `User.tenantId`.**
Sigue sin tocarse por la misma razón que antes: todo el codebase confía en
`User.tenantId` como escalar único (`@@unique([tenantId, email])`,
`/auth/me`, `changePassword`, `updateProfile`, y ~26 sitios que hacen
`getTenantDb().user.findUnique({where:{id: getUserId()}})` confiando en que
RLS ya los limita al tenant correcto).

**`TenantMembership`** (RLS **estándar**, `tenantId` = el tenant **cliente**,
NOT NULL — cae automáticamente bajo `tenant-scoped-tables.rls-spec.ts` sin
necesitar ninguna excepción, mismo patrón que las 40+ tablas existentes).
El vínculo ahora es **tenant↔tenant**, no user↔tenant:

```
id
tenantId          // tenant cliente, dueño de la relación
homeTenantId      // tenant del ESTUDIO CONTABLE (no un User individual)
inviteeIdentifier // email o CUIT del tenant/estudio invitado, hasta que se resuelve
direction         // CLIENT_INVITED | ACCOUNTANT_REQUESTED
status            // PENDING | ACCEPTED | DECLINED | REVOKED
initiatedByUserId // quien disparó la fila (siempre alguien con contexto propio en ese momento)
respondedAt
createdAt
```

**`TenantMembershipLink`** (tabla nueva, RLS estándar por `tenantId` =
tenant cliente): la identidad de auditoría **sigue siendo por persona, no
por estudio** — esto es deliberado y es la parte que preserva el punto 2
(identidad/auditoría) intacto a pesar de que el permiso ahora es
compartido. Si 3 contadores del mismo estudio accedieran con una única fila
`User` "espejo" compartida, sus acciones volverían a ser indistinguibles
entre sí — exactamente el mismo problema que tiene hoy la impersonación.
Por eso, la fila `User` espejo dentro del tenant cliente se sigue creando
**por persona**, pero ahora de forma perezosa (lazy) la primera vez que ESE
usuario puntual del estudio activa una sesión en ESE cliente puntual — no
al aceptar la membresía (que es a nivel estudio, no a nivel persona):

```
id
membershipId    // FK a TenantMembership
studioUserId    // User.id del contador puntual, en SU tenant (el estudio)
linkedUserId    // User.id "espejo" de ESE contador puntual, DENTRO del tenant cliente
createdAt
```

**Cómo se elige el tenant activo por request — igual mecanismo que hoy, sin
tocar nada del núcleo**: el tenant activo sigue siendo 100% una propiedad
del JWT (`tenantId` claim), decidido en el momento de emitir el token, nunca
por-request. Se agrega un endpoint nuevo, estructuralmente idéntico a
`POST /admin/tenants/:id/impersonate` pero gateado distinto:

`POST /memberships/:id/activate` — el chequeo de pertenencia es ahora **más
simple** que en la versión individual del diseño, porque no hace falta
cruzar contra ningún campo adicional: `membership.homeTenantId ===
request.user.tenantId` (el tenant del JWT ya verificado del usuario que
llama — es literalmente su propio tenant, el del estudio) **&&**
`membership.status === 'ACCEPTED'`. Dentro de `withTenantContext(clientTenantId)`
busca (o, si es la primera vez que ESTE usuario puntual entra a ESTE
cliente, crea) el `TenantMembershipLink` correspondiente y su
`linkedUserId`, y llama `buildAccessToken(linkedUser, clientTenantId,
moduleAccess, {expiresIn: <configurable, ver más abajo>})` — la MISMA
función que ya usa login/impersonate, sin cambios. El frontend reusa el
mismo patrón client-side de `apps/web/src/lib/impersonation.ts` (guardar el
token "hogar", swap al token del tenant cliente, restaurar al volver a la
cartera).

**Quién dentro del estudio puede hacer qué** (usando roles ya existentes,
sin inventar nada nuevo): crear/aceptar/revocar una `TenantMembership`
(la relación estudio↔cliente en sí) queda gateado a `@Roles('OWNER','ADMIN')`
del estudio — es una decisión administrativa del estudio, no de cualquier
empleado. **Activar** una sesión en un cliente ya-aceptado (`POST
/memberships/:id/activate`) puede hacerlo cualquier usuario del estudio con
rol `OWNER`/`ADMIN`/`ACCOUNTANT` (no `VIEWER`/`SALES`/etc.) — es trabajo del
día a día, no una decisión administrativa nueva cada vez.

**Impacto en `@@unique([tenantId, email])`**: ninguno, igual que antes — la
fila espejo (ahora en `TenantMembershipLink.linkedUserId`) sigue siendo una
fila real dentro del tenant cliente, con su propio `(tenantId, email)`
válido. Sigue sin haber ninguna FK nueva que cruce tenants (mismo argumento
que antes respecto al antecedente de `composite_tenant_fks`).

**Impacto en JWT/`JwtAuthGuard`**: cero, igual que antes.

**El problema estructural real, y cómo se resuelve** (mismo mecanismo que
`list_tenant_ids()`, ahora parametrizado por `tenantId` del estudio en vez
de por `userId` — lo cual además simplifica el chequeo de IDOR, ver punto 3):
1. Listar "las" membresías/invitaciones pendientes del estudio, sin importar
   el tenant destino → `list_studio_memberships(studio_tenant_id)`,
   `SECURITY DEFINER`, `GRANT EXECUTE` acotado a `plexo_app`. El único
   chequeo de seguridad que necesita esta función es que quien la invoque
   pase su propio `request.user.tenantId` — no hace falta cruzar contra un
   usuario puntual.
2. Crear una solicitud dirigida a un tenant en el que el estudio todavía no
   tiene contexto (`ACCOUNTANT_REQUESTED`) → misma función de escritura que
   antes, ahora recibe `homeTenantId` en vez de `homeUserId`.
3. Aceptar/rechazar una invitación recibida, y crear/reusar el
   `TenantMembershipLink` + fila espejo al activar → sigue siendo, sin duda,
   **la pieza de más escrutinio de todo el diseño**: nunca acepta ningún id
   de actor desde el body/params, siempre `request.user.tenantId`/`.sub` del
   JWT ya verificado. Necesita su propio test dedicado (mismo espíritu que
   `cross-tenant-write.rls-spec.ts`, pero a nivel service: un estudio no
   puede activar/leer la membership de otro estudio).

Todo lo demás (el cliente invita, el cliente aprueba una solicitud, el
cliente revoca, cualquier lectura desde el lado del tenant cliente) usa RLS
estándar sin escape hatch, porque el cliente siempre opera dentro de su
propio contexto.

## 2. Identidad y auditoría del contador

Resuelto como efecto directo del punto 1, **preservado incluso con el
permiso ahora a nivel estudio**: cada contador puntual del estudio tiene su
propia fila `TenantMembershipLink.linkedUserId`, una fila `User` real y
permanente dentro del tenant cliente (no un usuario prestado como en la
impersonación, y no compartida entre los distintos contadores del mismo
estudio). Toda escritura durante una sesión activada por membership queda
en `UserActivityLog`/`AuditLog` con `userId` = ese `linkedUserId` puntual —
una identidad única y estable por persona, que el propio visor de auditoría
del tenant cliente resuelve correctamente a "Juan Pérez (Contador, Estudio
XYZ)", nunca ambigua entre los distintos contadores del mismo estudio ni
con la ambigüedad que tiene hoy la impersonación. No hace falta ningún
cambio en `ActivityLogInterceptor`, `computeDiff`, ni en el trigger de
`audit_log_capture()` — `app.user_id` ya se setea solo, automáticamente,
porque `TenantContextInterceptor` ya pasa `request.user.sub` (el
`linkedUserId` de esa persona puntual) a `withTenantContext` en cada
request, sin cambios.

## 3. Alcance y seguridad

**Recomendación de alcance para esta v1 (justificada)**: solo lectura por
defecto en un set curado de módulos relevantes para un contador (`taxes`,
`accounting`, `invoicing`, `reports`, `receivables`, `payables`),
auto-otorgado al aceptar la membresía vía `UserModuleAccess` — creando ahí,
por primera vez, filas reales para ese `linkedUserId` (hoy esa tabla no
tiene NINGÚN endpoint de creación en toda la app; se construye solo la
escritura mínima puntual para este flujo, **no** un CRUD genérico de
`UserModuleAccess` — eso queda fuera de alcance de la Fase 1). Escritura
explícita solo en `taxes`, apoyándose en el único precedente real que ya
existe en el código (`managedByAccountant` en
`libs/modules/taxes/src/lib/taxes.service.ts`, que ya distingue "esto se le
puede delegar a un `ACCOUNTANT`" en producción). Nada de escritura en
Inventario/Ventas/Compras/POS por defecto — son módulos operativos, no
contables/fiscales.

**Caminos de fuga posibles y cómo el diseño los previene** (con el
antecedente real de las 2 fugas ya encontradas en mente):
- **Tabla nueva sin RLS** (clase del incidente de `add_purchases_module`,
  7 tablas sin `RLS`/`GRANT` hasta que un curl real lo reveló) → mitigado:
  `TenantMembership` sigue el patrón estándar de tenant, cae automático
  dentro de `tenant-scoped-tables.rls-spec.ts` sin necesitar ninguna
  excepción — el test ya existente lo cubre el mismo día que se migre.
- **FK simple cross-tenant** (clase de la fuga corregida en
  `composite_tenant_fks`) → el diseño la evita por construcción: no hay
  ninguna FK nueva que cruce de un tenant a otro, porque la identidad del
  contador "vive" como fila real en cada tenant al que tiene acceso.
- **IDOR en las 2 funciones `SECURITY DEFINER` nuevas** → la única fuga real
  posible de todo el diseño, porque ahí RLS no protege nada. Mitigación:
  disciplina de código (nunca aceptar el id del actor desde el body/params,
  siempre desde el JWT verificado) + test dedicado obligatorio antes de
  cerrar esta fase. Con el vínculo a nivel estudio (no por usuario) este
  chequeo es además más simple que en la primera versión del diseño: alcanza
  con comparar `request.user.tenantId` (el propio tenant del JWT ya
  verificado) contra `homeTenantId`, sin cruzar contra un `userId`
  individual.
- **Un empleado del estudio con rol de bajo privilegio activando acceso a un
  cliente sin que el estudio realmente lo haya autorizado** → mitigado
  separando "quién puede crear/aceptar/revocar la relación con un cliente"
  (`@Roles('OWNER','ADMIN')` del estudio, decisión administrativa) de "quién
  puede activar una sesión en un cliente ya aceptado" (`OWNER`/`ADMIN`/
  `ACCOUNTANT`, trabajo del día a día) — un `VIEWER`/`SALES`/etc. del estudio
  nunca puede activar nada, ni aunque la membership ya esté `ACCEPTED`.
- **Token de sesión de membership sin revocación activa** — mismo límite que
  ya tiene hoy la impersonación (`JwtAuthGuard` no re-consulta DB, así que
  revocar no invalida un JWT ya emitido hasta que expira). No es un límite
  nuevo que este diseño introduzca, se hereda tal cual; se mitiga con una
  expiración acotada y configurable (ver sección dedicada más abajo), más
  larga que los 15min de impersonación porque acá sí se espera una sesión de
  trabajo real, pero igual lejos de un login normal de 8h/30d.
- **Fila espejo reusable tras revocar** → revocar una membership tiene que
  poner `status: SUSPENDED` en el `linkedUserId` (mismo mecanismo de
  `UserStatus` que ya se chequea hoy en `login()`), y el flujo de activación
  debe re-chequear `membership.status === 'ACCEPTED'` cada vez (no solo al
  invitar), para que una membership revocada no pueda reactivarse sin pasar
  de nuevo por todo el flujo.

## 4. Vista de cartera + consolidado

Mismo patrón exacto que `AdminTenantsService.listTenants()`/
`AdminAuditService.listActivity()`: `list_studio_memberships()` (función
nueva del punto 1) da la lista de tenantIds ACCEPTED del **estudio** (no de
un contador puntual — la cartera es del estudio, cualquier usuario con rol
habilitado la ve entera; ver "Decisiones confirmadas" sobre este punto),
después un loop de `withTenantContext(tenantId)` por cada uno junta un
resumen (`TenantSettings.ownTaxCondition`, conteos de facturación,
vencimientos próximos del punto 5).

**Costo, honestamente**: cada iteración abre su propia transacción
(`withTenantContext` envuelve en `$transaction`), igual que hace
`AdminTenantsService` hoy — el propio comentario de ese archivo ya asume
recorrido secuencial con try/catch por tenant (no en paralelo, para no
tumbar el panel entero si un tenant falla). Para un contador con una
cartera de decenas de clientes esto es aceptable; no escala indefinido.
Recomendación: la vista de cartera solo trae conteos livianos (no recalcula
`VatBookService.getSalesBook()` completo por cada tenant en cada carga de
pantalla — eso se reserva para cuando el contador entra a UN tenant
puntual), y cualquier cosa más pesada queda atrás de una acción explícita
de "actualizar" en vez de recalcularse en cada render.

## Duración del token de sesión — configurable por SuperAdmin

## 2. Cancelar una solicitud PENDING que inicié

**Decisión de diseño**: no crear un endpoint nuevo ni un status nuevo de
enum — **extender `MembershipsService.revoke()`** (mismo endpoint `POST
/memberships/:id/revoke`, ya usado desde ambos lados en el frontend) para
que además de cortar una relación `ACCEPTED` (comportamiento actual, sin
cambios), también pueda cancelar una `PENDING`:

```
if (membership.status === 'ACCEPTED') {
  // comportamiento actual sin cambios: cualquiera de las dos partes,
  // suspende las filas espejo ya creadas.
} else if (membership.status === 'PENDING') {
  // NUEVO: sólo el lado que inició la relación puede cancelarla -
  // mismo cálculo que expectedResponderTenantId de respond(), pero
  // invertido (el iniciador, no quien tiene que responder). Nunca
  // lee initiatedByUserId para la autorización (sigue sin usarse para
  // eso, igual que el resto del diseño) - el chequeo es a nivel
  // TENANT, no de usuario puntual, mismo criterio que respond().
  const expectedInitiatorTenantId =
    membership.direction === 'CLIENT_INVITED' ? membership.tenantId : membership.homeTenantId;
  if (expectedInitiatorTenantId !== callerTenantId) {
    throw new ForbiddenException('No podés cancelar una solicitud que no iniciaste vos');
  }
  // sin filas espejo que suspender todavía (activate() nunca corrió)
} else {
  throw new BadRequestException('Esta relación no se puede revocar/cancelar en su estado actual');
}
```

El mensaje de error genérico y el `updated.status = 'REVOKED'` quedan
iguales para los dos casos — "revocada"/"cancelada" es la misma
operación de fondo (cortar antes de que llegue a buen puerto), no hace
falta un status nuevo.

**Frontend**: en `PortfolioSection.tsx` (`PendingRow`) y
`ClientAccountantsSection.tsx` (`RelationRow`), la rama `else` que hoy
muestra "Esperando respuesta del cliente"/"—" sin botón pasa a mostrar un
botón "Cancelar" que llama al mismo `membershipsApi.revoke(id)` que ya
existe (reusa la mutation de revoke ya cableada para el caso ACCEPTED).

      const db = getTenantDb();

```prisma

// ACCOUNTANT del estudio (comportamiento actual, sin cambios) - con
// filas = sólo esos contadores puntuales (más OWNER/ADMIN del estudio,

model TenantMembershipAssignment {

}
```

(+ `assignments TenantMembershipAssignment[]` en `TenantMembership`).

Nueva migración (`..._membership_assignment/migration.sql`): tabla nueva
con RLS+GRANT estándar (cae automático bajo
`tenant-scoped-tables.rls-spec.ts`, sin excepción) + regenerar
`list_studio_memberships()` para que devuelva también el conjunto de
asignados por fila. Postgres no permite cambiar las columnas de
`RETURNS TABLE` con `CREATE OR REPLACE` - hace falta `DROP FUNCTION` +
`CREATE FUNCTION` de nuevo, mismo cuerpo que hoy más un `LEFT JOIN` contra
la tabla nueva y `array_agg(...) FILTER (WHERE ...)` agrupado por fila de
membership, devolviendo `assigned_studio_user_ids text[]` (vacío si no
hay ninguna asignación):

```sql
SELECT m.id, m."tenantId", t.name, m.direction::text, m.status::text,
       m."inviteeIdentifier", m."createdAt", m."respondedAt",
       COALESCE(array_agg(a."studioUserId") FILTER (WHERE a."studioUserId" IS NOT NULL), '{}')
FROM tenant_memberships m
JOIN tenants t ON t.id = m."tenantId"
LEFT JOIN tenant_membership_assignments a ON a."tenantId" = m."tenantId" AND a."membershipId" = m.id
WHERE m."homeTenantId" = p_studio_tenant_id
GROUP BY m.id, m."tenantId", t.name, m.direction, m.status, m."inviteeIdentifier", m."createdAt", m."respondedAt"
ORDER BY m."createdAt" DESC;
```

**Endpoint nuevo**: `PUT /memberships/:id/assignments`, body
`{studioUserIds: string[]}` - reemplaza el conjunto completo en una sola
llamada (semántica PUT, mapea directo a un multi-select que manda todo lo
tildado; evita tener que diffear altas/bajas). Gateado `ADMIN_ROLES`
(mismo criterio que crear/aceptar/revocar - decisión administrativa del
estudio). Antes de saltar al tenant cliente, valida que CADA id de
`studioUserIds` sea realmente un usuario del PROPIO tenant del que llama
(`getTenantDb().user.findMany({where:{id:{in:studioUserIds},
tenantId:callerTenantId}})`, todavía en contexto propio del estudio,
comparando el conteo) - nunca confía en ids ajenos pasados por el body.
Después, dentro de `withTenantContext(clientTenantId)`: borra todas las
asignaciones existentes de esa membership y crea las nuevas
(`deleteMany` + `createMany`, reemplazo simple).

**Filtrado por visibilidad**: helper puro `filterVisibleForCaller(rows,
callerRole, callerUserId)` - si `callerRole` es `OWNER`/`ADMIN`, devuelve
todo sin cambios; si no (`ACCOUNTANT`), filtra a
`assignedStudioUserIds.length === 0 || assignedStudioUserIds.includes(callerUserId)`.
Se aplica en los 3 lugares donde importa "qué ve/puede tocar ESTE caller
puntual" - la ruta `GET /memberships`, `getPortfolio()`, y `activate()`
(filtrando el resultado de `listMine()` ANTES de buscar el `id` pedido -
un contador sin asignación que intenta activar un cliente ajeno recibe el
mismo "Membership not found" que si la fila no existiera, mismo patrón
IDOR-safe que ya usa el resto del diseño). **No** se aplica en
`requestFromStudio()` (chequeo de duplicados) ni en
`resolveMembershipClientTenantId()` (necesitan la verdad completa, no la
vista filtrada de un caller puntual). `listMine()` en sí queda sin tocar,
siempre devuelve todo con el array completo de asignados - el filtro es
una capa aparte por-callsite, no un parámetro nuevo de la función.

**Frontend** (`PortfolioSection.tsx`): cada tarjeta de cliente gana un
multi-select "Asignado a" (sólo visible/editable para OWNER/ADMIN del
estudio, vía el mismo `profile.role` que ya usan otras partes de
`AppShell`) - opciones = cada miembro del propio equipo, reusando
`teamApi.list()` (`apps/web/src/lib/team.ts`, ya existe, sin endpoint
nuevo de listado); ninguna opción tildada = "todo el estudio" (estado por
defecto, retrocompatible). Un `<select multiple>` nativo alcanza para
esta sub-fase (mismo criterio de simplicidad que el resto del frontend de
este módulo - sin librería de multi-select nueva). Nuevo
`membershipsApi.setAssignments(id, studioUserIds)`.
